# Orchestrate 工具组折叠无响应排查

v2.3.1 在收起“排队工具”组时出现无响应。现场栈与隔离复现共同指向 Qt 6.11.2 的树控件无障碍节点缓存：折叠后缓存行号失效，Windows UI Automation 遍历可能循环。v2.3.2 在客户端同步清理这份缓存，并覆盖同类协作记录文件夹。

## 现场证据

现用便携包记录的版本为 2.3.1、源码提交为 `ad21d8e7dc528e81c017df18ca74e1667233e392`，Qt 版本为 6.11.2。以下时间均为 UTC+8。

- Windows 在 2026-11-09 16:06:11 记录 `RADAR_PRE_LEAK_64`，16:21:14 记录 `AppHangTransient`。进程存活，但窗口已出现“未响应”的系统替代窗口。
- 首次采样工作集峰值为 5,440,647,168 字节（约 5.1 GiB），主线程累计 CPU 约 6 分钟。峰值和 CPU 累计值覆盖该进程整个生命周期；后续现场采样另观察到私有内存升至 8,344,694,784 字节（约 7.8 GiB），随后回落并反复增长。
- 两次附加调试均在主线程看到 `UIAutomationCore.dll`、COM 调用及 Qt Windows 事件循环。栈采集后立即脱离调试器；最初的系统故障记录早于本轮窗口检查。
- 现用数据库以 SQLite 只读方式检查，`PRAGMA quick_check` 返回 `ok`，检查前后文件 SHA256 相同。数据库中只有 5 个工具，协作记录正文最大约 5 千字符。

这些证据支持界面无障碍遍历异常，未识别具体由哪个无障碍客户端发起读取。不能仅凭已加载的输入法或其他模块将责任归给相应软件。

## 隔离复现

用相同 Qt 库构建不连接任何工具的最小程序：创建两列树、三个分组和每组一个子项，先读取各项的 `QAccessibleInterface` 以填充缓存，再收起中间分组。

旧实现中，`child(8)` 仍返回已经隐藏的中间组子项，但 `indexOfChild(child(8))` 返回 0；后续节点也保留旧位置。Windows UIA 的 NextSibling 使用 `indexOfChild + 1` 查找下一个节点，因此可以回到已遍历的节点。测试采用有界检查，不实际运行无限遍历。修复前退出码为 1，修复后每个节点都满足 `indexOfChild(child(i)) == i`，退出码为 0。

本机 Qt 源码的 `QTreeViewPrivate::collapse` 移除可见行时没有同步重置缓存；`QAccessibleTree::child` 按旧行号取缓存，而 `indexOfChild` 按新的可见行计算位置。这一差异解释了复现结果，并与用户操作及现场栈一致。

## 修复与验证

`treeaccessibility.h` 使用公开的 Qt 无障碍接口，在展开和折叠信号中同步发送模型重置；无障碍尚未激活但已有缓存时，也立即清理缓存。自动化工具树和协作记录文件夹树均接入。协作记录搜索会阻断树控件信号，因此在批量隐藏或展开完成后，显式完成布局并同步节点映射，包括可见行数相同但内容变化的情况。

本地新增回归覆盖两种实际页面、无障碍激活与未激活、每组反复折叠展开 20 次，以及搜索切换。既核对节点位置，也核对名称与唯一身份，并在处理下一轮事件前断言正确性。专项分别通过 Qt offscreen 和 Windows 原生平台，共 7 passed / 0 failed；原生验证检查 Qt 提供的接口，不等同于对所有外部 UIA 客户端的长期压力测试。

完整 20 个 CTest 套件通过，HeadingTextTest 为 63 passed / 0 failed。测试、现场栈与最小复现保存在忽略目录 `app/tests/` 和 `app/build-qt/diagnostics/hang-20261109/`，不进入发布包。数据库仍为 schema v6，未修改工具命令或周期读取策略。
