# Treat independently running automation as a first-class monitoring target

> 实现状态（2026-09-29）：本 ADR 的领域边界保留，但原先提出的进程/日志混合接入、独立受监测任务配置和产物目录字段尚未实现。当前仅通过声明中的状态文件读取结果，刷新开关属于工具注册；心跳、服务健康和周期过期由工具计算。适配时以 [接入指南](../automation-tool-contract-v1.md) 为准。

Orchestrate 不仅监测由自己发起的工具运行，也支持登记已经在本地或服务器上独立运行的自动化任务。这样可以覆盖持续运行、定时自行启动或由其他系统启动的任务；代价是必须区分“Orchestrate 发起的一次工具运行”和“Orchestrate 观察到的受监测任务”，并为后者定义稳定的识别、状态和失联规则。

第一版通过本地进程、SSH 目标、输出、日志和心跳信息获取状态，不要求部署专用 Agent。接入采用混合模式：现有工具可以通过进程和日志接入；能够配合 Orchestrate 的工具则优先提供结构化状态或心跳信息。每个受监测任务都有独立的“启用监测”开关，启用后 Orchestrate 重启可以自动恢复监测。

自动化工具可以同时拥有可执行的工具命令和受监测任务。对于不是由 Orchestrate 启动的受监测任务，Orchestrate 默认只提供监测；如果需要停止，必须由用户明确登记停止命令，不按进程名、PID 或任务 ID 默认强制终止。

## Consequences

- 自动化工具可以同时拥有工具命令和受监测任务配置。
- 不能把任意外部任务直接伪装成工具运行；二者的开始时间、启动者和可控制性不同。
- Orchestrate 重启后可以恢复启用中的受监测任务。
- 仅依赖进程名或 PID 会遇到重启、多个实例和 PID 复用问题；后续需要确定一个可跨进程/跨服务器实现的识别或心跳约定。
- 工具命令的工作目录和产物目录是分开的配置；Orchestrate 记录产物目录，但不假设任意命令会自动使用它。
